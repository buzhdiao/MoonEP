# 第二章 总体架构与分层设计

> 本章自顶向下审视 MoonEP 的整体结构：它分了几层，每层为什么存在，层与层之间用什么语言对话；一个缓冲区对象从构造到销毁经历了什么；一次前向与一次反向在流与事件的意义上如何编排。读完本章，读者应当能对照仓库目录说出每个模块的职责与依赖方向，并理解通信计划对象为什么被设计成四次算子调用之间的中心契约。细节留待后续各章：规划算法在第三章，各内核的数据通路在第五至八章，内存布局在第九章，内核工程在第十章。

## 2.1 三层结构总览

MoonEP 的代码分为三层，语言与职责都不同。这种分层不是装饰性的——每一层对应一类不可替代的系统能力，层间边界由编译工具链天然划清。

第一层是 Python 编排层，由 moonep/api.py、moonep/buffer.py、moonep/constants.py 与 moonep/__init__.py 组成。这一层持有全部长生命周期资源：卡间共享缓冲区、预取池、归约池、屏障槽位。它对上层暴露一个极小的类接口，即缓冲区类的四个通信算子加一个销毁方法；对下层则负责把张量指针、形状与配置逐个传给设备内核的宿主入口。校验逻辑也集中在这里：参数的类型与取值检查、张量的形状与数据类型检查、以及各种不变量的断言，都在进入设备代码之前完成，这在第十一章有专节论证——把错误拦在宿主侧，比让设备内核在自旋里静默挂死要人道得多。

第二层是设备内核层，全部用 CUTLASS Python 方言（CuTe DSL）写成，由九个模块组成：规划内核 moonep/planning.py、分发主内核 moonep/dispatch.py、分发尾声 moonep/dispatch_epilogue.py、汇合前置 moonep/combine_prologue.py、汇合主内核 moonep/combine.py、梯度归约 moonep/grad_reduce.py、权重预取 moonep/prefetch.py、跨进程同步 moonep/inter_rank_sync.py、以及三者的公共原语库 moonep/_common.py。这一层的每一个文件都遵循同一个模式：一个内核类持有全部编译期常量，一个带即时编译装饰器的宿主入口负责布局构造与发射，一批按参数缓存编译产物的包装函数避免重复编译。这一层是本文的主体，第五至十章逐个解剖。

第三层是驱动适配层，由 csrc/nvl_shared_buffer.cuh 与 csrc/bindings.cu 组成，经编译成为扩展模块 moonep._C。这一层存在的理由是：跨进程共享虚拟内存与组播对象的注册必须走 CUDA 驱动应用编程接口（cuMemCreate、cuMemMap、cuMulticastCreate 等），而 PyTorch 没有暴露这些能力。第三层做了且只做了这一件事：分配、导出句柄、映射、绑定组播、查询粒度、释放。它不懂张量语义，不懂通信计划，甚至不懂 rank 的概念——它只知道块、句柄与字节数。

三层的依赖是严格单向的：编排层调用内核层的发射入口与驱动层的扩展函数；内核层只依赖自身的公共原语库与常量，不回过头调用编排层；驱动层完全不感知上两层。这条单向纪律带来一个测试上的红利：第九章的缓冲区原语可以脱离通信语义单独测试，第十一章的校验逻辑可以在无设备的环境下测试。

## 2.2 缓冲区对象与它的上下文

编排层的核心是一个叫 Buffer 的类，位于 moonep/api.py。它包裹了一个被称为上下文的字典，由模块级函数 _create_context 预构造。上下文持有全部预分配的资源，包括：本进程的隐状态通信分片（按进程数平铺成长条），一张进程间共享的元数据缓冲（路由权重的别名区、规划输出区、划痕区、屏障槽位都在其中，第九章给出完整布局图），以及规划输出张量组、去重结构张量组、跨进程栅栏计数器等本地张量。上下文是纯内部结构，外界只通过 Buffer 的方法触达它；销毁方法负责把上下文持有的全部卡间映射逐一解除。

Buffer 的构造参数只有六个：输入令牌数 S、隐状态维度 H、路由选择数 K、专家总数 E、进程数 R、以及两个可选参数——内核占用的流多处理器数目（缺省取三十二与设备上限的较小者）和填充粒度（缺省一百二十八）。构造完成后，四个通信算子的签名从此固定：分发、预取权重、汇合、归约梯度。这种一处构造、处处静态的风格是刻意的：上下文里预分配的每一个缓冲都按最坏情况取大小，此后没有任何一条通信路径需要再分配显存，也没有任何一条路径需要把设备上的计数器读回宿主侧来确定形状。README 把这一点列为设计支柱的第三条——静态形状——而它的实现起点就是上下文构造函数里的这一批预分配。

值得指出的是，epn 等于 E 除以 R 这一恒等式在上下文构造处被断言强制：专家总数必须能被进程数整除。这不是数值上的限制，而是设计上的选择——本地专家数同时定义了预取槽位数与归约槽位数，三章将说明这两个角色共用一个数字正是规划约束得以简洁的原因。

Buffer 还暴露两个只读视图属性：本进程隐状态分片的视图与路由权重缓冲的视图。它们存在的意义是让零拷贝模式成为可能——框架可以把专家前馈网络的输出原位写进通信缓冲区，汇合时省去一次边界拷贝。视图的有效期是脆弱的：下一次分发或汇合会覆写缓冲内容，因此文档明确警告使用者不得把视图保存到下一次通信之后，自动微分框架也不得为了反向而暂存它们。这类契约无法用类型系统表达，只能靠文档与第十一章的运行期断言共同维护。

## 2.3 通信计划：四次调用之间的中心契约

如果说上下文是静态资源的容器，通信计划就是动态信息的载体。规划内核每次运行产出一份计划，封装为 moonep/planning.py 中的不可变数据类 MoonEPCommPlan。它的字段可以分为三组。

第一组是路由与分段信息：目的地表（长度为 N 的整数张量，每个路由项写着一个目的槽位的线性编号；重复路由项被编码为负数，其绝对值减一即原始目的地编号——这个编码让分发内核能用一个符号判断跳过整行拷贝，是去重机制的枢纽）、分组偏移表（长度为两倍 epn，指出每个专家槽位的令牌段结束位置，供分组矩阵乘直接使用）、零填充区间表（两倍 epn 行乘二，指出每个段需要清零的起止）、远端统计量（两个整数：需要本进程权重副本的远端专家总数与各来源触发计数）。

第二组是搬迁信息：待拷贝专家清单（按目的进程分块的整数矩阵，每行列出该进程需要哪些远端专家的权重副本，空槽用负一填充）。预取内核据此构造推送任务；归约内核也据此判断哪些槽位在本步被占用。

第三组是去重结构：重复组表（每行三元组：主行槽位、重复段起点、重复段长度）、重复槽位平铺表、以及一个二元计数器（有效前缀长度）。这三张表由分发内核在全新规划路径上构建，随后被分发尾声与汇合前置两个内核消费。它们的生命周期横跨一次前向的多个内核与一次反向的多次复用，因此被计划对象持有而非被某个内核私有。

计划对象身上的一个重要注释值得全文引用：生产端构建器用原子加法追加记录，因此重复组表与重复槽位表的元素顺序不保证稳定，逐次运行会不同；测试必须比较集合语义而非逐元素顺序。这个看似工程琐事的注释实际上宣告了一条测试方法论——第九章的参考实现刻意采用确定性顺序，两者比较时必须经过语义化的比较器，第十一章的测试工具为此提供了专用断言。此外，计划对象提供深拷贝方法，共享标量配置而复制全部设备张量，供需要多份独立计划的场景使用。

计划在四次算子调用之间流转的完整路线是：前向分发产出计划；前向预取与后向归约各消费一次；前向汇合消费一次；反向汇合（隐状态梯度的归并）消费一次；反向分发的实现——用原计划重发输出梯度——把计划原样再消费一次。也就是说，一份计划被典型的训练迭代使用五次。复用的安全性来自两个事实：其一，计划描述的是路由拓扑而非数据内容，只要路由表不变，它就描述同一次通信；其二，所有被计划引用的张量都在上下文或计划内预分配，复用不产生新的资源需求。第四章将给出参考实现与不变量校验，证明复用路径与全新路径产出语义一致的结果。

## 2.4 流与事件：通信如何与计算重叠

MoonEP 的四个算子都接受一个异步完成参数。缺省路径上，算子在当前流上同步发射；开启异步后，算子把全部内核发射到内部通信流，并返回一个事件对象供调用方在计算流上等待。这个简单的机制支撑了最重要的重叠模式：框架在计算流上发起分发（异步），立刻转到其他无关工作（例如注意力层或下一层的权重预取），直到真正需要分发结果时才等待事件。

为什么通信需要独立于计算的流？因为分发与专家计算是天然可重叠的：分发把令牌送到远端的同时，本地可以继续为已经就绪的段启动矩阵乘；而如果两者在同一流上排队，重叠就不存在了。独立流的代价是同步复杂度——跨流使用张量必须登记到流的记录表里，防止缓存分配器在另一条流还在读写时把内存复用给别人。编排层为此提供了内部的流记录辅助方法，在每次异步发射前把所有参战张量登记到通信流上。这类细节在 PyTorch 的异步执行模型里是必须的，也经常是并发缺陷的温床，MoonEP 把它收敛成一处。

还有一个更细粒度的重叠机制贯穿各内核：程序化依赖启动。传统上，同一流上的两个内核之间有一条硬边界——前一个完全退出，后一个才能启动——这个空档对微小内核是不可忽略的。程序化依赖启动允许后继内核在前驱仍在运行时提前就位，由前驱在合适的时机发出触发信号，后继再显式等待前驱的写入可见。分发尾声在启动后立刻等待分发的最后写入，汇合前置则在结束时触发汇合的提前启动。第十章将展开这个机制的语义与陷阱。

在一切重叠之外，还有一个最朴素的同步器：跨进程对齐内核，位于 moonep/inter_rank_sync.py。它是一个单线程块的小内核，所有进程各自发射一个，通过共享元数据缓冲里的屏障槽位互相等待。它的用途单一而讲究：在规划内核发射之前把所有进程对齐，使规划与通信的计时少受宿主延迟或上游流相位差的影响。汇合算子缺省在暂存之前也执行一次这样的对齐，可通过参数关闭——因为汇合内核内部在入口处还有一道更便宜的跨进程屏障，第十章将比较这两道屏障的成本与语义。

## 2.6 编译期特化与缓存

设备内核层有一个贯穿始终的性能设计：把一切能搬到编译期的都搬到编译期。每个内核类的构造函数收下的参数——进程数、专家数、令牌数、槽位数、填充粒度、元数据步长——全部变成即时编译的常量表达式，生成的设备代码为这组配置单独特化：循环边界被展开、分支被常量折叠、共享内存大小被静态计算。宿主入口再用按参数元组缓存的装饰器把编译产物存起来，同一配置只编译一次，之后每次调用只是重新构造指针参数并发射。

这种特化风格有一处特别值得注意的应用：汇合内核的装载流水线级数不是固定的，而是按隐状态维度与设备的单块共享内存上限，在候选集里从大到小自动挑选——第七章给出挑选公式。调用方因此不需要为不同的隐维度手工分派级数，这正是方言化内核相对手写汇编的核心红利：编译期元程序可以做静态资源规划，而接口仍然保持形状无关。

常量层 moonep/constants.py 虽然只有二十几行，却是规划、分发与测试三方共享的唯一真源：秩编号字段与选择索引字段的位宽（都是七位，前者覆盖一百二十八个进程的规模上限，后者刻意放宽为将来非位掩码编码留余地）、以及每个分发线程块中构建去重结构的线程束数（四个，由延迟分析选定，第五章详述）。把这些数字放进独立模块而不是散落在内核里，目的就是让测试与生产代码引用同一份定义——一旦某处编码超出位宽，断言会在构造期而不是在设备上失败。

## 2.7 生命周期与资源安全

缓冲区对象的生命周期有四个阶段：构造（校验参数、初始化进程组、预分配全部缓冲）、使用（四次算子反复调用）、销毁（同步所有流、解除卡间映射、释放组播对象与屏障槽位）、析构兜底。设计者在这里做了两件超出常规的事情。

第一，销毁是显式且必经的。销毁方法先做一次跨进程同步，确保没有别的进程还在读本进程的缓冲，再逐一释放；文档明确要求在进程组析构之前调用它，因为组播对象的解除绑定依赖进程组仍然存在。第二，析构函数是双模式的：若使用者忘了显式销毁，对象被回收时会根据配置自动销毁或发出资源告警——宁可告警也不静默泄漏驱动层的句柄，因为这类句柄泄漏在多进程场景下会让整个进程组的其他成员挂在等待上。第十一章的测试基建进一步兜底：每个测试结束后自动销毁所有仍然活跃的缓冲对象，保证用例之间不互相污染。

## 2.9 公开接口的签名走读

本章末尾把四个算子的签名完整走读一遍，作为后续各章的接口地图。走读的依据是 moonep/api.py 的模块文档字符串与 Buffer 类的方法定义，以及 README 的接口演示。

分发算子的完整形态接收四个张量：隐状态（S 行乘 H 列，半精度）、路由权重（S 行乘 K 列，单精度）、路由表（同形状整数）、每专家计数（长度 E 的整数向量）。返回四样东西：分发后的隐状态（槽位数乘 H，半精度，位于共享分片上）、分发后的路由权重（槽位数长，单精度）、分组偏移表（两倍 epn 的整数）、以及通信计划对象。当传入计划参数而非路由输入时，算子进入复用模式：跳过规划，直接按既定计划搬运。三个可选开关横跨全部算子：异步完成（把发射挪到内部通信流并返回事件，第二章第四节）、零拷贝（返回缓冲视图并要求专家计算原位读写，第五、六章的契约）、跨进程预对齐（汇合缺省开启的一次额外对齐）。

预取权重算子接收计划与六组张量：三个投影的本地权重（epn 乘 H 乘 H 撇）与三个投影的全组预取池（R 乘 epn 乘 H 乘 H 撇）。量化专家时，权重以字节形态给出，另附三组本地缩放因子（第八章）。它没有返回值——效果是原地把权重写进各进程的池。

汇合算子接收计划、专家输出（槽位数乘 H）与可选的分发后权重；返回令牌主序输出（S 乘 H）与可选的回收权重矩阵（S 乘 K）。归约梯度算子接收计划、三个投影的本地梯度（epn 乘 H 乘 H 撇，单精度）与三个投影的全组归约池；同样无返回值，效果是把副本梯度累加进本地梯度并清零消费过的槽位。

走读这四个签名可以发现一个统一的模式：凡是"数据流进 MoonEP"的算子（分发正向、汇合反向）都返回视图或新张量，凡是"数据从 MoonEP 的共享缓冲出发"的算子（预取、归约）都原地生效。这个模式让调用方的内存管理职责清晰：返回的视图受生命周期契约约束，原地写入的效果由算子保证。另一个模式是计划参数的位置：它在四个算子里都是第一个命名参数——计划是这条链路的脊柱，接口形状忠实于架构。

## 2.10 与计算图捕获的兼容性

现代训练流水线常用计算图捕获消除发射开销：把一段固定形状的工作录制下来，之后每步只回放。捕获对被录制的代码有一条苛刻的要求——全程不得有宿主同步，因为同步会把捕获中的流与宿主线程序列化，捕获立即失败。

MoonEP 的全链路为此做了系统性设计：所有形状静态预分配（没有按需分配就没有分配器同步）、所有工作量决策在设备端（前置与归约的计数器由内核自己读，第二章）、所有跨进程协调走设备内屏障（第十章）。收益被基准脚本直接兑现：预取与归约基准在预热后把几十次迭代捕获成单张计算图再回放计时，捕获成功本身就是"无宿主同步"这一架构承诺的运行期验证。对集成方而言，这意味着 MoonEP 可以整体嵌进被捕获的训练段，不必为通信部分开例外。

计划对象在捕获场景下有一个值得注意的细节：计划是宿主侧的不可变对象，持有设备张量引用；捕获期间计划内容不变，回放时各内核从捕获好的指针读取。由于计划在捕获前产出（规划本身发生在捕获段之外或之内皆可——基准里两种都有先例），回放语义与即时执行语义一致。这类兼容性不是偶然的，它是第二章第七节生命周期设计（预分配、显式销毁、无隐式同步）的自然结果。

## 2.12 从目录树看架构

把第二章的分层论述落到仓库的目录树上，让结构与文件一一对应。根目录下的四个一级目录与两个文件家族构成全部：moonep 是 Python 主包，csrc 是驱动适配层，tests 是测试体系，benchmarks 是基准脚本，papers 收录参考模型与论文，figure 收录文档配图与生成脚本。

moonep 包内部的文件顺序本身就是一张架构图：入口模块只导出两个符号（缓冲类与计划类，包的初始化文件把公开面收窄到最小）；编排层三个文件——接口模块（缓冲类与上下文）、缓冲原语模块（第九章）、常量模块（第二章第六节）；内核层九个文件按依赖深度排列——公共原语库在最底、规划与主数据面居中、尾声前置与独立同步内核在侧翼。csrc 的两个文件各自只有一件事：实现与绑定。tests 的文件按"工具在前、测试在后"排列：路由生成器、内核测试工具、参考实现是三件公共设施，六个测试文件对应六个被测面。benchmarks 四个脚本分别覆盖通信算子、预取、归约与横向对比。

目录树给出的一个验证视角是"文件职责的单值性"：任何一个文件都能用一句话说清职责（本章第二节的分层表），任何一句话的职责都能定位到唯一文件。做不到这两点的仓库通常意味着分层已经腐化——MoonEP 的树在这一点上保持了克制，全仓库约一万五千行代码，没有出现两个文件争夺同一职责的情况。

## 2.14 分层的四个不变量

作为分层论述的总收束，把跨层的不变量列出来——它们是任何重构或扩展都必须保持的性质。不变量一，单向依赖：上层调用下层，下层从不回调（第二节）；违反它意味着循环依赖，即时编译与测试隔离都会失效。不变量二，校验前置：一切参数与张量检查发生在编排层，内核假定输入合法（第十一章第一节）；违反它意味着错误进入设备后以挂死或错值的形式出现，排查成本上升一个量级。不变量三，预分配完毕：运行期（四个算子的执行路径）没有任何显存分配与宿主同步（第二、七节）；违反它意味着计算图捕获失败、以及每步的分配器抖动。不变量四，命名一致：槽位、计划、段、分块等核心术语在三层里指同一个东西（第十二章第十七节的观察）；违反它意味着文档与代码互相说谎。四条不变量同时是四章的总结——架构（本章）、校验（第十一章）、静态形状（第三章）、术语（第十二章）——分层不是目录结构，是这四条性质的代名词。

## 2.16 上下文字典的字段清单

缓冲对象包裹的上下文字典（本章第二节）值得给出字段清单——它是全部预分配资源的注册表。设备侧资源四类：隐状态分片（按进程数堆叠的长条，本进程持有其中一块的映射，第九章第七节）；元数据缓冲（单条按进程分块的整数长条，内含权重别名区、计数区、规划输出区、暂存区、屏障槽位与来源区，第九章第六节）；规划输出的本地张量组（计划对象的四张表，第四章第七节）；本地划痕与栅栏计数（规划内核与软件栅栏的私有工作区）。配置类字段：全部规模参数（进程数、专家数、每卡专家数、逻辑槽位数及其补齐值、填充粒度、元数据步长与各分区偏移——第三节的构造函数把它们一次算清）。运行态字段：去重核数（环境变量覆写后的实际值）、缓冲大小日志（构造完成时在零号进程打印一次，第十一章第十三节的算子口径与之一致）。

清单给出的一个工程判断是：上下文是"构造期算好、运行期只读"的快照——运行态字段在构造后不再变化，算子的每次执行只是把快照里的指针与常量传给内核。这个只读性是线程安全与捕获兼容（第二章第十节）的基础，也是调试时可以放心打印整个上下文的原因：它在进程生命周期内是常量。

## 2.17 本章小结

本章给出了 MoonEP 的鸟瞰：三层结构各自的存在理由；以预分配上下文为基础的静态形状体系；以通信计划为中心的五次调用契约；以独立通信流与程序化依赖启动为手段的重叠编排；单向的模块依赖纪律；以及编译期特化加缓存的内核工程风格。接下来三章深入本文的技术核心——规划系统：第三章把规划形式化为带约束的再指派问题并推导缓冲容量上界，第四章解剖规划内核的四阶段实现及其正确性体系。
